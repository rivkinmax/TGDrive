Ты — опытный архитектор и разработчик настольных приложений для Windows. Твоя задача — спроектировать и реализовать надёжное приложение для синхронизации локальной папки с облачным хранилищем на базе Telegram.

Все требования ниже считаются согласованными. Если встречается техническая неоднозначность, выбирай наиболее безопасное, стабильное и консервативное решение, не нарушая основные ограничения, и явно фиксируй такое решение в документации.

==================================================
1. Общая цель приложения
==================================================

Создай приложение для Windows, которое делает локальную папку пользователя синхронизированной копией облачного хранилища, размещённого в одном приватном Telegram-канале.

Основная идея:

- пользователь выбирает локальную папку;
- всё содержимое этой папки синхронизируется с приватным Telegram-каналом;
- изменение файла на одном устройстве после синхронизации должно приводить к изменению файла в Telegram и на других устройствах;
- удаление, переименование, перемещение и изменение файлов также должно реплицироваться между устройствами;
- приложение должно быть рассчитано на работу нескольких устройств с одинаковым доступом к одному и тому же хранилищу.

==================================================
2. Главные технологические ограничения
==================================================

Использовать:

- только Windows;
- TDLib;
- пользовательский аккаунт Telegram;
- один приватный Telegram-канал как единственное облачное хранилище;
- локальную папку как основную пользовательскую копию данных.

Запрещено использовать:

- ботов;
- Bot API как основной транспорт;
- личные «Сохранённые сообщения»;
- несколько чатов как разделы диска;
- топики форумной группы;
- веб-интерфейс;
- заранее создаваемые стандартные папки вроде Documents, Photos, Videos и т.п.;
- серверные компоненты, внешние веб-сервисы, webhook-серверы и собственные облачные бэкенды.

Дополнительно:

- отдельный смонтированный диск через WinFsp не является обязательным для первой версии;
- основной интерфейс работы с данными — обычная локальная папка;
- если в будущем потребуется дисковый режим, он может быть добавлен отдельно через WinFsp, но не должен усложнять текущую архитектуру.

==================================================
3. Модель хранения данных
==================================================

Использовать режим:

«Полная локальная копия + копия в Telegram».

Это означает:

- локальная папка содержит актуальную пользовательскую копию файлов;
- приватный Telegram-канал содержит облачную копию файлов и метаданные;
- приложение отвечает за двустороннюю синхронизацию между локальной папкой и Telegram;
- локальная папка является полноценной рабочей копией, а не только кэшем.

При этом дополнительно должен использоваться служебный кэш, но только для технических целей:

- временные файлы при скачивании;
- временные файлы при загрузке;
- незавершённые операции;
- конфликтные копии;
- временные снимки изменяемых файлов;
- служебные базы и очереди;
- логи.

Кэш не должен считаться отдельной пользовательской копией облака.

==================================================
4. Абстрагирование служебных данных от папки облака
==================================================

Служебные данные приложения должны быть абстрагированы от пользовательской папки синхронизации.

Обязательно:

- точка хранения служебных данных настраивается отдельно;
- служебные данные не должны по умолчанию находиться внутри синхронизируемой папки;
- пользователь может выбрать отдельный путь для служебных данных;
- приложение должно работать, даже если папка синхронизации и папка служебных данных находятся на разных дисках.

Служебная папка должна хранить как минимум:

- конфигурацию;
- базу данных синхронизации;
- сессию и локальную базу TDLib;
- кэш временных файлов;
- логи;
- очереди операций;
- идентификатор устройства;
- данные о привязке к каналу;
- данные о привязке к локальной папке.

Пример логического разделения:

- папка облака:
  D:\MyTelegramCloud

- служебная папка:
  C:\Users\User\AppData\Roaming\TGDrive
  или любой другой путь по выбору пользователя.

==================================================
5. Авторизация и работа с Telegram
==================================================

Использовать только пользовательский аккаунт Telegram через TDLib.

Требования:

- поддержка входа по номеру телефона, коду и облачному паролю, если включена двухфакторная аутентификация;
- не хранить пароль в открытом виде;
- хранить сессию в служебной папке;
- по возможности защищать сессию средствами Windows, например DPAPI, если это уместно;
- поддерживать повторный вход после перезапуска без повторной авторизации, если сессия действительна;
- явно показывать ошибки авторизации, сети, ограничений и блокировок.

Приложение должно работать только с одним приватным каналом, выбранным пользователем.

Требования к каналу:

- канал должен быть приватным;
- пользователь должен иметь права на публикацию, редактирование и удаление сообщений;
- приложение должно проверять права доступа к каналу;
- если канал публичный или имеет посторонних участников, показать предупреждение;
- не использовать другие чаты, личные сообщения, несколько каналов или топики.

==================================================
6. Локальная папка и структура данных
==================================================

Пользователь сам указывает папку, которая будет связана с облаком.

Требования:

- не создавать заранее стандартные папки;
- не навязывать шаблоны структуры;
- структура папки должна отражать структуру облака;
- если папка пустая, приложение может подготовить её;
- если папка уже содержит данные, нужно выполнить безопасное начальное согласование с каналом;
- нельзя молча удалять или перезаписывать существующие локальные данные при первом запуске;
- если канал пустой, локальные файлы могут быть загружены как начальное содержимое;
- если канал уже содержит данные, а локальная папка пустая, приложение должно скачать данные;
- если и локальная папка, и канал содержат данные, выполнить сверку и показать конфликты пользователю.

Приложение должно поддерживать:

- вложенные папки;
- кириллицу и Unicode в именах файлов и папок;
- длинные пути, насколько это возможно в Windows;
- переименование файлов и папок;
- перемещение файлов и папок;
- удаление файлов и папок;
- создание пустых папок, если это возможно реализовать через служебные метаданные.

==================================================
7. Исключаемые временные и системные файлы
==================================================

По умолчанию нужно исключить из синхронизации типовые временные и системные файлы, чтобы не создавать лишнюю нагрузку и конфликты.

Например:

- *.tmp
- *.temp
- ~*
- desktop.ini
- Thumbs.db
- .DS_Store
- временные файлы редакторов
- файлы блокировок
- каталоги кэша браузеров и сборщиков, если пользователь явно не решил иначе

Список исключений должен быть настраиваемым.

Если пользователь хочет синхронизировать всё, он должен иметь возможность отключить или изменить исключения.

==================================================
8. Синхронизация изменений
==================================================

Основной принцип:

«Изменил на одном устройстве — после синхронизации изменилось в облаке и на других устройствах».

Требования:

- синхронизация должна быть двусторонней;
- изменение локального файла должно приводить к обновлению облака после сохранения файла;
- нельзя загружать файл в облако на каждое промежуточное изменение, пока приложение или редактор продолжает писать в файл;
- нужно дожидаться стабилизации файла: завершение записи, отсутствие изменений размера и времени модификации, возможность чтения файла;
- после успешной загрузки локальная база данных должна обновиться;
- приложение должно избегать повторной загрузки того же самого содержимого, если хэш и версия не изменились.

Для обнаружения изменений использовать:

- FileSystemWatcher;
- дополнительную проверку стабильности файла;
- сравнение размера, времени изменения и хэша;
- очередь фоновых задач.

Если файл временно заблокирован другим процессом:

- повторять попытку с экспоненциальной задержкой;
- показывать статус в интерфейсе;
- не блокировать всю очередь синхронизации из-за одного файла.

==================================================
9. Кэширование и временные файлы
==================================================

Так как используется полная локальная копия, постоянный контентный кэш всех файлов не нужен.

Однако служебный кэш необходим для надёжности операций.

Кэш должен использоваться для:

- скачивания файла во временный файл с последующей проверкой целостности;
- подготовки файла к загрузке, если исходный файл может меняться;
- хранения незавершённых загрузок и выгрузок;
- конфликтных копий;
- восстановления после сбоев;
- временных данных при перестроении индекса.

Требования к кэшу:

- кэш размещается в служебной папке;
- кэш должен иметь ограниченный размер;
- старые временные файлы должны очищаться;
- незавершённые загрузки не должны попадать в пользовательскую папку как готовые файлы;
- после успешного скачивания файл должен атомарно перемещаться в целевую папку;
- после успешной загрузки файла в Telegram временные данные могут удаляться, если они больше не нужны;
- пользователь должен иметь возможность вручную очистить кэш.

==================================================
10. Метаданные в Telegram
==================================================

Каждый синхронизируемый файл должен представляться в Telegram отдельным сообщением с документом.

Обязательное требование:

- путь к файлу должен храниться в подписи к файлу.

Дополнительно в подпись можно и нужно добавить машиночитаемые метаданные, если это не нарушает лимиты Telegram.

Рекомендуемый набор полей:

- версия формата метаданных;
- тип записи: file, folder, tombstone, service;
- file_id — стабильный уникальный идентификатор файла;
- version_id — уникальный идентификатор конкретной версии;
- path — относительный путь файла внутри папки облака;
- sha256 — хэш содержимого файла;
- size — размер файла;
- mtime_utc — время последнего изменения в UTC;
- device_id — идентификатор устройства, создавшего версию;
- prev_version_id — идентификатор предыдущей версии, если есть;
- при необходимости другие служебные поля.

Путь должен храниться в нормализованном виде:

- относительно корня облака;
- с прямыми слэшами;
- без ведущего слэша;
- без выхода за пределы корня;
- без использования «..».

Пример логики подписи:

- путь обязателен;
- file_id важнее имени файла;
- при переименовании или перемещении file_id должен сохраняться;
- при изменении содержимого создаётся новая версия с новым version_id;
- при удалении файла создаётся служебная запись об удалении, если это необходимо для надёжной репликации.

==================================================
11. Переименование и перемещение
==================================================

Переименование и перемещение файлов и папок должно синхронизироваться.

Требования:

- если содержимое файла не изменилось, не нужно заново загружать файл;
- по возможности следует отредактировать подпись существующего сообщения, чтобы обновить путь;
- если редактирование подписи невозможно или запрещено, нужно создать служебную запись перепривязки пути;
- локальная база данных должна обновляться независимо от того, удалось ли отредактировать подпись сразу;
- перемещение папки должно обновлять пути всех файлов внутри неё;
- операция должна быть идемпотентной и безопасной при повторе.

==================================================
12. Версионность файлов
==================================================

Поддержать версионность файлов.

Правила:

- каждая новая версия файла загружается как отдельное сообщение;
- старая версия не должна молча теряться;
- текущая версия — актуальная версия файла;
- старые версии должны храниться 6 месяцев с момента создания версии;
- после 6 месяцев старые версии могут удаляться;
- текущая версия не удаляется по возрасту;
- очистка старых версий должна выполняться постепенно, чтобы не создавать массовую нагрузку на Telegram;
- пользователь должен видеть прогресс очистки старых версий.

Восстановление версии:

- пользователь может просмотреть доступные версии файла, если они известны локальной базе и/или находятся в канале;
- восстановление старой версии должно создавать новую текущую версию, а не ломать историю;
- восстановление должно быть безопасным и подтверждаться пользователем.

==================================================
13. Удаление данных
==================================================

Удаление должно реплицироваться между устройствами.

Требования:

- если пользователь удаляет файл или папку на одном устройстве, после синхронизации это изменение должно распространиться на облако и другие устройства;
- удаление должно быть контролируемым и не должно приводить к мгновенной необратимой потере данных из-за случайной ошибки;
- для надёжной репликации удаления использовать служебные записи, например tombstone;
- tombstone должен содержать идентификатор удалённого объекта, путь, время удаления и устройство;
- tombstone не должен быть пользовательским файлом;
- срок хранения tombstone и удалённых версий должен быть разумным и настраиваемым;
- массовое удаление должно выполняться осторожно, с паузами и прогрессом.

Если пользователь удаляет данные вручную прямо в Telegram вне приложения:

- приложение не должно молча ломаться;
- при обнаружении несоответствия нужно показать понятное предупреждение;
- по возможности предложить восстановить объект из локальной копии или подтвердить удаление;
- ручные изменения в канале вне приложения считаются нежелательными и должны документироваться как рискованные.

==================================================
14. Конфликты
==================================================

Основное правило разрешения конфликтов:

«Спросить пользователя».

Конфликт возникает, если:

- один и тот же файл изменён на нескольких устройствах до синхронизации;
- локальная версия и удалённая версия расходятся;
- файл переименован, перемещён или удалён одновременно с изменением содержимого;
- обнаружено расхождение между локальной базой, локальным файлом и каналом;
- невозможно безопасно применить изменение автоматически.

Требования к конфликту:

- показать пользователю диалог с понятной информацией;
- показать путь файла, устройство, время, размер и, если возможно, хэш;
- предложить варианты:
  - оставить локальную версию;
  - оставить удалённую версию;
  - сохранить обе версии как конфликтные копии;
  - отложить решение.
- нельзя молча перезаписывать конфликтные данные;
- если пользователь недоступен или диалог не может быть показан, синхронизацию проблемного файла нужно приостановить и пометить как конфликтную;
- конфликтные файлы должны получать понятные имена, например:
  имя_файла_конфликт_дата_время_устройство.расширение

==================================================
15. Много устройств и репликация
==================================================

Приложение должно поддерживать репликацию данных между несколькими устройствами.

Сценарий:

- пользователь использует один и тот же пользовательский аккаунт Telegram на нескольких устройствах;
- каждое устройство имеет свою локальную копию папки;
- каждое устройство имеет свою служебную папку;
- все устройства синхронизируются с одним и тем же приватным каналом.

Требования:

- каждое устройство должно иметь уникальный device_id;
- device_id сохраняется в служебных данных устройства;
- метаданные версий должны включать device_id;
- приложение должно различать собственные изменения и изменения с других устройств;
- нельзя зацикливаться: скачанное изменение не должно восприниматься как новое локальное изменение и снова загружаться;
- нужна защита от петель синхронизации;
- нужна идемпотентность операций;
- нужна устойчивая обработка ситуации, когда устройство долго было офлайн.

Если устройство долго не было в сети:

- после появления сети синхронизация должна выполняться постепенно;
- нельзя мгновенно отправлять тысячи операций;
- пользователь должен видеть прогресс;
- ошибки должны обрабатываться с повтором и паузами.

==================================================
16. Темп репликации и защита от блокировок
==================================================

Это критически важное требование.

Приложение должно работать с Telegram максимально осторожно, чтобы не вызывать ограничения, временные блокировки или подозрительную активность.

Обязательно реализовать:

- очередь операций;
- низкую агрессивность по умолчанию;
- адаптивное ограничение скорости;
- паузы между операциями;
- случайные небольшие задержки;
- обработку FLOOD_WAIT и аналогичных ошибок;
- экспоненциальный повтор при сетевых сбоях;
- приостановку синхронизации после серии ошибок;
- ограничение числа одновременных операций;
- приоритет пользовательских действий над фоновыми операциями.

Рекомендуемый профиль по умолчанию:

- один активный исходящий файл за раз;
- небольшая пауза между загрузками;
- дебаунс локальных изменений;
- отложенная загрузка файлов до стабилизации;
- пакетная, но не массовая обработка начальной синхронизации;
- запрет на агрессивное массовое удаление сообщений.

Пользователь может иметь несколько профилей скорости:

- осторожный;
- обычный;
- быстрый.

Быстрый профиль должен включать предупреждение о рисках.

При получении ограничений от Telegram:

- остановить активные операции;
- выждать требуемое время;
- снизить темп после возобновления;
- показать пользователю понятное сообщение;
- не пытаться обходить ограничения.

==================================================
17. Локальная база данных
==================================================

Использовать локальную базу данных, например SQLite.

База должна хранить как минимум:

- идентификатор устройства;
- идентификатор связанного канала;
- путь к папке синхронизации;
- путь к служебной папке;
- список известных файлов;
- список известных папок;
- текущие версии файлов;
- старые версии файлов;
- хэши;
- размеры;
- время изменения;
- message_id соответствующих сообщений в Telegram;
- статусы синхронизации;
- очередь исходящих операций;
- очередь входящих операций;
- конфликтные состояния;
- tombstone;
- данные о последней успешной синхронизации.

Требования:

- база должна быть устойчива к сбоям питания и аварийному завершению;
- операции должны быть идемпотентными;
- приложение должно уметь восстанавливать состояние после сбоя;
- повреждение базы не должно приводить к молчаливой потере пользовательских данных;
- должна быть функция перестроения базы из Telegram.

==================================================
18. Перестроение структуры и восстановление базы
==================================================

Реализовать функцию восстановления или перестроения локальной базы данных из Telegram.

Требования:

- восстановление должно сканировать канал и находить сообщения с метаданными приложения;
- пользователь должен видеть подробный прогресс;
- прогресс должен включать этапы, количество обработанных сообщений, найденные файлы, ошибки и примерное оставшееся время;
- восстановление можно отменить;
- после восстановления приложение должно продолжить работу безопасно;
- если часть метаданных повреждена, нужно логировать проблему и по возможности восстановить данные частично;
- восстановление не должно удалять локальные файлы без подтверждения.

Приложение должно быть настольным приложением для Windows.

Не использовать веб-интерфейс.

Рекомендуемый интерфейс:

- иконка в трее;
- основное окно состояния;

==================================================
20. Первоначальная настройка
==================================================

Мастер настройки должен включать:

1. Авторизацию пользователя в Telegram через TDLib.
2. Выбор приватного канала для хранилища.
3. Выбор локальной папки облака.
4. Выбор служебной папки приложения.
5. Выбор профиля скорости синхронизации.
6. Подтверждение начала синхронизации.

Если канал пустой:

- предложить загрузить содержимое локальной папки как начальное облако.

Если локальная папка пустая:

- предложить скачать содержимое канала.

Если обе стороны содержат данные:

- выполнить сверку;
- показать найденные конфликты;
- не выполнять молчаливое объединение с потерей данных.

==================================================
21. Обработка ошибок и устойчивость
==================================================

Приложение должно быть устойчиво к типовым сбоям:

- потеря сети;
- выход из аккаунта;
- истечение сессии;
- отсутствие прав на канал;
- удаление канала;
- недоступность локальной папки;
- переполнение диска;
- блокировка файла другим процессом;
- повреждение временного файла;
- несовпадение хэша;
- длинные пути;
- недопустимые имена файлов;
- превышение лимитов Telegram;
- конфликт одновременных изменений;
- сбой питания;
- аварийное завершение приложения.

Требования:

- ошибки должны быть понятными пользователю;
- критические ошибки должны останавливать проблемную операцию, а не всю систему, если это возможно;
- нужно вести журнал ошибок;
- нельзя молча терять данные;
- нельзя молча перезаписывать конфликтные файлы;
- нужно сохранять незавершённые операции и продолжать их после перезапуска.

==================================================
22. Безопасность и приватность
==================================================

Поскольку используется пользовательский аккаунт и приватный канал:

- не использовать публичные каналы;
- предупреждать, если канал имеет посторонних участников;
- не отправлять данные на сторонние серверы;
- не использовать аналитику и телеметрию;
- хранить служебные данные только локально;
- защищать сессию по мере возможностей ОС;
- не хранить пароли в открытом виде;
- не логировать конфиденциальные данные, токены, пароли, коды авторизации;
- предусмотреть возможность выхода из аккаунта с очисткой сессии.

Клиентское шифрование в базовой версии не является обязательным, если пользователь явно не запросит его позже. Если шифрование будет добавляться, оно должно быть опциональным и не ломать метаданные синхронизации.

==================================================
23. Ограничения по файлам
==================================================

Большие файлы в текущей версии не являются приоритетом.

Требования:

- не реализовывать обязательную схему разбиения больших файлов на части;
- ввести настраиваемый максимальный размер файла;
- если файл превышает лимит, показать ошибку и не блокировать очередь;
- по умолчанию установить разумный лимит, который не должен вызывать проблемы с Telegram;
- пользователь может изменить лимит, но должен быть предупреждён о рисках.

==================================================
27. Критерии приёмки
==================================================

Приложение считается выполненным, если:

1. Пользователь может войти в свой аккаунт Telegram через TDLib.
2. Пользователь может выбрать один приватный канал.
3. Пользователь может выбрать локальную папку.
4. Пользователь может выбрать отдельную служебную папку.
5. Локальная папка синхронизируется с каналом.
6. Изменение файла локально после сохранения приводит к обновлению файла в Telegram.
7. Изменение файла на другом устройстве после синхронизации появляется в канале и на первом устройстве.
8. Переименование, перемещение и удаление файлов реплицируются.
9. Конфликты показываются пользователю и не перезаписываются молча.
10. Версии файлов хранятся и очищаются по правилу 6 месяцев.
11. Приложение использует осторожный темп синхронизации и уважает ограничения Telegram.
12. Служебные данные не привязаны жёстко к папке облака.
13. Приложение не использует ботов, топики, несколько чатов, веб-интерфейс и стандартные шаблоны папок.
14. Длительные операции показывают понятный прогресс.
15. Приложение переживает сетевые сбои, перезапуск и конфликты без молчаливой потери данных.
